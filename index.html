End-to-end picture

Your text becomes tokens; tokens become vectors; vectors flow through a transformer; the model outputs probabilities over the next token. Agents wrap that loop with tools and feed results back as more tokens.

Why it matters for design

Latency and cost both scale with tokens-in plus tokens-out. Anything you append (system prompt, RAG chunks, tool JSON) is more input cost.

Why it matters for behavior

Agents amplify both successes and failures: a bad tool result pollutes the context for every following turn.

Tokens — the unit the model actually sees

Models do not consume words or characters. They consume tokens: integer IDs from a fixed vocabulary built by a tokenizer. A token can be a word, a syllable, a few characters, punctuation, or a byte sequence.

2. Why subwords (instead of words or letters)?

  • Word-level vocabularies explode in size and can't represent typos, names, or new words.
  • Character-level sequences become too long; the model wastes capacity learning English spelling.
  • Subword (BPE / WordPiece / SentencePiece) keeps common words as one token and splits rare ones — the sweet spot.

3. Try it: rough English heuristic

For everyday English prose: ~4 chars/token or ~¾ word/token. Code, JSON, URLs, and non-Latin scripts can be 2× or 3× more expensive.

4. Where token cost actually lives

  • System prompt + tools schema: sent on every turn unless prompt caching applies.
  • Conversation history: grows linearly; older turns rarely earn their keep.
  • Tool outputs: raw API responses are usually the worst offender. Truncate or summarize.
  • Generated tokens: billed separately (often more expensive than input).

Vectors — coordinates of meaning

A vector (a.k.a. embedding) is just a list of numbers that acts as a digital fingerprint for a token's meaning. Lat/long is a 2-D vector that locates a place; a 384-D embedding locates a meaning in a 384-dimensional space.

1. The mental model: 3 dimensions you can picture

Imagine 3 axes — "Animal-like", "Fluffy", "Electronic":

WordVector [animal, fluffy, electronic]Reading
Dog[0.9, 0.8, 0.1]high animal, high fluff, low electronic
Cat[0.9, 0.9, 0.1]nearly identical to Dog → nearby in space
Laptop[0.1, 0.1, 0.9]opposite corner

"Dog" and "Cat" share neighbors in real text, so the math forces their vectors to look alike. The model never reads the word "animal" — it just notices similar numbers.

2. Why 384 (or 768, or 4096) dimensions?

More dimensions = more room for nuance: noun vs verb, formal vs slang, finance vs medical, sentiment, tense, register. Each dimension is an abstract trait the model invented during training; humans rarely have words for them.

Narrower (e.g. 128)

Cheap, fast, "dumber" — collapses subtle meaning differences.

Wider (e.g. 4096)

Expensive, more nuance — what frontier LLMs use as their internal "workspace width."

3. A 10-D financial example

For a "high-growth tech stock" the model might learn something like:

#ConceptValueWhy

"Nvidia" and "Bitcoin" land near each other in this space because they share high values along Risk, Tech, and Growth — the model treats them as conversational neighbors without any dictionary.

5. Where this shows up in apps

  • Semantic search / RAG: embed the query, find nearest chunks in a vector DB, stuff them into the prompt.
  • Clustering support tickets, deduping content, recommendation.
  • Classification: cheap classifier on top of frozen embeddings.
Design takeaway: RAG quality depends more on chunking, metadata, and choice of embedding model than on prompt wording.

3. What the human actually decides

  • Architecture: dimensions (e.g. 384), number of layers, attention heads.
  • Diet: the dataset — TinyStories vs financial filings vs cooking recipes. Same word, different vector ends up.
  • Patience: epochs, learning rate, batch size. More practice → finer distinctions, until overfitting kicks in.
Same word, different worlds: "Apple" trained on finance lands near "Microsoft, stock". Trained on recipes it lands near "cinnamon, pie".

Transformer — what those vectors flow through

A transformer is a stack of identical "blocks". Each block lets every token's vector look at every other token's vector (attention) and then refine itself locally (feed-forward). After N blocks, each vector is a contextual summary of the whole sentence.

1. One block, in slow motion

2. Why this design wins

Parallelism

Unlike RNNs, all positions are processed simultaneously — fits GPUs perfectly.

Long-range dependencies

Attention is direct: "dog" can look at "the boy" 50 tokens earlier in one hop.

Composable

Same block for text, code, images (ViT), audio. The architecture is modality-agnostic.

The cost

Naive attention is O(n²) in sequence length — that's why long-context models are expensive.

3. Decoder vs encoder

  • Decoder-only (GPT, Llama, Mistral, Claude): trained to predict the next token. Causal mask. Used for chat, code generation, agents.
  • Encoder-only (BERT, embedding models): bidirectional context. Best for classification, embeddings, retrieval.
  • Encoder–decoder (T5, original Transformer): translation, summarization where you read one thing and write another.

Generation — one token at a time

Decoder LLMs are autoregressive: at each step the model emits a probability distribution over the entire vocabulary; you sample one token, append it to the context, and run again until a stop condition.

3. Stopping & cost

  • EOS token — the model's natural "done" marker.
  • max_tokens — your safety belt; always set it.
  • Stop sequences — e.g. "\nUser:" in custom chat formats.
Inference cost ≈ (input tokens) + (output tokens). Output tokens are usually more expensive per token than input — so trim outputs aggressively.

Agents — LLM + tools + control loop

An agent is your application code repeatedly calling an LLM. The model can ask to run tools (function calls, HTTP, DB queries, code). Your orchestrator runs them and feeds the results back into the next call as more tokens.

1. The control flow

2. The hidden token cost of agents

Each turn re-sends the entire conversation, including every prior tool output. Five tool calls of 2 KB each is ~10 KB extra context on the next call — and the next, and the next.

Cap observation size

Truncate tool responses to top-N rows, JSON pick fields, or run a "summarize" pass before re-injecting.

Narrow tool schemas

Smaller, well-typed schemas reduce hallucinated arguments and shrink the system prompt.

Step budget

Hard-cap iterations (e.g. max_steps = 8). Otherwise an agent in doubt will loop forever.

Validate server-side

The model can request anything — your code is the actual security boundary.

3. Common patterns

  • ReAct: think → call tool → observe → repeat. Most common.
  • Plan-then-execute: make a plan once, then execute steps with smaller calls.
  • Multi-agent: orchestrator + specialists. Powerful but token-heavy; worth it only when one model truly can't handle the task.

Token efficiency — practical levers

Same behavior, fewer tokens, fewer round-trips. Most wins come from what you put in, not clever prompting tricks.

Before vs after

The big levers, in order

  1. Prompt caching (where supported): keep the system prompt + tool schemas byte-stable at the start of every request.
  2. Bound observations: never paste raw tool output beyond, say, 1–2 KB without summarization.
  3. Summarize history: replace turns older than N with a 1-paragraph rolling summary.
  4. Structured outputs: ask for JSON / enums; prevents the model from adding filler prose.
  5. Smaller model for sub-tasks: classification, routing, extraction can run on a cheap model and feed a bigger one.
  6. Stream + early-stop: stop sequences and max_tokens protect against runaway output.

Anti-patterns

  • Embedding entire docs in the system prompt instead of using RAG.
  • Passing full HTTP responses as tool observations "just in case".
  • Unsummarized multi-day chat history.
  • Few-shot examples that duplicate what the schema already says.
  • Polite filler ("certainly!", "let me think..."). Cheap individually, expensive at scale.
Measure before you optimize. Log tokens-in / tokens-out per request and per tool. The biggest cost is usually one tool you forgot you had.
